# خطة دمج الذكاء الاصطناعي الصوتي في Voice SIP Agent

**الحالة:** خطة تنفيذ معتمدة — لا تغييرات تشغيلية على جسر SIP-SIM في هذه المرحلة  
**الفرع:** `feat/realtime-ai-voice-integration-plan`  
**الفرع الأساس:** `feat/telegram-voice-fallback`

## 1. القرار المعماري

إضافة وضع اختياري باسم **AI Voice Agent** داخل المشروع الحالي، مع إبقاء مسار المكالمات الحالي هو المسار الأساسي والاحتياطي.

- **مرجع الجودة الأول للاختبار:** OpenAI Realtime `gpt-realtime-2.1` لأنه النموذج الأكثر قدرة.
- **مرشح خفض التكلفة:** `gpt-realtime-2.1-mini`؛ نقارنه على نفس عينات اللهجة اليمنية ولا نعتمده للإنتاج إلا إذا اجتاز معايير الجودة والمقاطعة.
- **النقل:** WebSocket آمن من الهاتف/الخادم الوسيط إلى Realtime API.
- **جسر SIP-SIM:** يبقى مسؤولاً عن استقبال المكالمة الخلوية، وإدارة SIP/RTP، والتقاط صوت المكالمة، وإنهائها. لا نستبدله بـ Asterisk أو LiveKit.
- **مفتاح API:** لا يوضع داخل APK أو إعدادات Android. يحفظ في خدمة وسيطة موثوقة على الخادم الداخلي.
- **التفعيل:** ميزة اختيارية، مع مفتاح تشغيل/إيقاف، وتبقى معطلة افتراضياً حتى اجتياز اختبارات الصوت.

### لماذا WebSocket وليس SIP مباشر إلى OpenAI؟

توثيق OpenAI SIP يصف استقبال المكالمات عبر SIP trunk/provider يوجّه الاتصال إلى عنوان OpenAI. المشروع الحالي عبارة عن بوابة Android ذات SIP registrar داخلي وشريحة SIM، وليس SIP trunk تجارياً. لذلك فإن تمرير الصوت من نقطة الجسر الحالية إلى Realtime عبر WebSocket يحافظ على بنية المكالمة الحالية ويجنب إدخال مزود SIP إضافي. يمكن إعادة تقييم SIP المباشر لاحقاً إذا أضيف trunk فعلي.

## 2. شكل تدفق المكالمة المستهدف

```
شبكة المشغل
    |
    v
هاتف Android + SIM
    |
    v
جسر SIP-SIM الحالي (اتصال/حالة/RTP/صوت خلوي)
    |                         |
    | audio uplink             | audio downlink
    v                         ^
AudioFrameTap                 AudioFrameSink
    |                         ^
    v                         |
خدمة Voice AI Gateway <--> OpenAI Realtime WebSocket
    |
    +-- إعدادات الجلسة واللهجة والتعليمات
    +-- إحصاءات الاستخدام والتكلفة
    +-- إغلاق الجلسة عند إنهاء المكالمة
```

**قاعدة عدم كسر الجسر:** لا يُحذف أو يُعاد كتابة مسار SIP/RTP الحالي. نضيف واجهة صوت مجردة عند حدّ الجسر، بحيث يمكن اختيار أحد المسارات:
1. `BRIDGE`: السلوك الحالي كما هو.
2. `AI`: يوجّه صوت المتصل إلى المحرك، ويعيد صوت المحرك إلى مسار الإرسال الخلوي.
3. `MONITOR`: يظل الصوت متاحاً للمراقبة/التشخيص دون أن يرسل صوتاً آلياً إلى المتصل.

يجب تحديد نقطة الإدخال والإخراج الدقيقة بعد مراجعة ملفات تنفيذ الجسر، لا بالتخمين من أسماء الأصناف.

## 3. تنسيق الصوت

توثيق Realtime يدعم:
- G.711 μ-law (`audio/pcmu`, 8 kHz).
- G.711 A-law (`audio/pcma`, 8 kHz).
- PCM mono 16-bit عند 24 kHz أو 16 kHz.

المشروع يذكر أن بناء SIP الحالي يستخدم G.711. لذلك:
- نتحقق أولاً من الـ codec المتفاوض عليه فعلياً في RTP ومن صيغة الصوت الخارجة من التقاط TELEPHONY_TX/RX.
- إذا كانت إطارات الجسر مطابقة لـ PCMU أو PCMA، نفضّل تمريرها دون تحويل غير ضروري.
- إذا كان مصدر الصوت PCM، نستخدم resampling مضبوطاً إلى الصيغة التي تضبط بها جلسة Realtime.
- يجب أن تتطابق صيغة الإدخال والإخراج في جلسة WebSocket الواحدة؛ لا نفترض أن تغيير إعداد الصيغة يحوّل البيانات تلقائياً.
- لا نرسل WAV headers؛ نرسل عينات الصوت الخام وفق الصيغة المختارة.

## 4. مكونات التنفيذ

### Android (Kotlin)
- `AiCallController`: إدارة دورة حياة جلسة AI لكل مكالمة.
- `AudioFrameTap`: قراءة نسخة من صوت المتصل دون تعطيل الجسر الحالي.
- `AudioFrameSink`: إدخال صوت الرد إلى مسار الإرسال الخلوي مع منع تكرار/صدى صوت المتصل.
- `AiModeSettings`: تفعيل AI، اختيار المحرك، سياسة fallback، والحد الأقصى لمدة المكالمة.
- `CallSessionRegistry`: ربط معرف مكالمة SIP بمعرف جلسة AI ومنع تسرب الصوت بين المكالمات.

### Voice AI Gateway (الخادم الداخلي)
- WebSocket آمن بين Android والخادم.
- إدارة مفاتيح OpenAI والاتصال بـ Realtime API.
- إعداد النموذج والصوت والتعليمات وVAD.
- مصادقة الأجهزة وتحديد معدل الاتصالات.
- تتبع الاستخدام لكل مكالمة دون تخزين PCM.
- إعادة الاتصال المنضبطة وإغلاق الجلسات والموارد.

### واجهة المزود
إنشاء عقد داخلي `VoiceAiProvider` حتى لا يرتبط الجسر مباشرة بـ OpenAI:
- `OpenAiRealtimeProvider` — التنفيذ الأول.
- `LocalPipelineProvider` — خيار احتياطي لاحق (STT + LLM + TTS محلي).
- لا نضيف LiveKit أو TEN كطبقة إلزامية في الإصدار الأول؛ هما إطارا تشغيل بديلان، وليسا شرطاً لتمرير صوت الجسر إلى Realtime.

## 5. تجربة العربية واللهجة اليمنية

لا نعتمد على وصف تسويقي لجودة العربية؛ نثبت الجودة باختبار صوتي فعلي. نص إعداد الجلسة يجب أن يطلب:
- التحدث بالعربية اليمنية الواضحة، مع التحول إلى الفصحى إذا تعذر فهم اللهجة.
- جمل قصيرة طبيعية، دون مبالغة في اللهجة أو تقليد غير دقيق.
- سؤال المتصل عند عدم وضوح الاسم أو الرقم بدلاً من التخمين.
- عدم اختلاق معلومات أو تنفيذ إجراء خارجي دون تأكيد.
- الإفصاح في بداية المكالمة بأن المتصل يتحدث مع مساعد آلي.

تُقارن نسختا Mini وRealtime الأعلى على نفس مجموعة عبارات يمنية (أسماء، أرقام، عناوين، مقاطعة المتحدث، ضوضاء اتصال خلوي).

## 6. المقارنة والتكلفة

بما أن الأولوية لجودة الصوت، نبدأ بالاختبار المرجعي على 2.1 الكامل، ثم نقارن Mini على نفس السيناريوهات؛ لا نعتمد Mini إلا إذا اجتاز معايير العربية والمقاطعة. الأسعار المنشورة في صفحة OpenAI وقت إعداد هذه الخطة:
- `gpt-realtime-2.1-mini`: صوت وارد $10 لكل مليون audio tokens، وصوت صادر $20 لكل مليون audio tokens.
- `gpt-realtime-2.1`: صوت وارد $32 لكل مليون audio tokens، وصوت صادر $64 لكل مليون audio tokens.

هذه أسعار tokens وليست تكلفة دقيقة ثابتة. لا نعتمد تقديراً شهرياً قبل قياس الاستهلاك الفعلي لمكالمة اختبار؛ فحجم الكلام، والصمت، ومدة إخراج الصوت، وإعدادات VAD تؤثر في الاستهلاك. يضاف استهلاك النص/الأدوات عند استخدامها.

## 7. خطة التنفيذ المرحلية

### المرحلة 0 — تدقيق نقطة الربط (قبل كتابة كود الصوت)
- تحديد موضع استقبال RTP وإرساله.
- تحديد نقطة التقاط صوت TELEPHONY_TX/RX وصيغة العينات ومعدلها.
- توثيق codec الفعلي واتجاهات الصوت.
- مراجعة معالجة إنهاء المكالمة، hold، mute، وmulti-call.
- استخراج خط أساس من سجلات التشخيص الحالية.

**بوابة النجاح:** رسم موثق لمسار الصوت الحالي في الاتجاهين، واختبار baseline لا يتغير.

### المرحلة 1 — خدمة Realtime مستقلة عن Android
- بناء خدمة Gateway صغيرة على الخادم الداخلي.
- إضافة WebSocket إلى OpenAI Realtime.
- إعداد مصادقة الجهاز ومفتاح API من متغيرات بيئة/secret store.
- اختبار ملف صوتي/مصدر PCM اصطناعي ثم بث حي محلي.
- تسجيل latency وusage وerrors دون تسجيل الصوت الخام.

**بوابة النجاح:** محادثة صوتية ثنائية الاتجاه عبر Gateway دون اتصالها بعد بجسر المكالمة.

### المرحلة 2 — محول الصوت داخل التطبيق
- إضافة واجهات Tap/Sink حول الجسر الحالي.
- ربط الجلسة بالمكالمة الصحيحة.
- تنفيذ queue محدودة للصوت، backpressure، وإسقاط الإطارات المتأخرة بدلاً من تراكم التأخير.
- التعامل مع تنسيق الصوت والتحويل عند الضرورة.
- إضافة زر/إعداد لتشغيل AI يدوياً في الاختبارات.

**بوابة النجاح:** تشغيل/إيقاف AI لا يغير سلوك BRIDGE عند تعطيله.

### المرحلة 3 — مكالمة SIM واحدة
- اختبار incoming SIM call.
- اختبار فهم الكلام والرد العربي.
- اختبار مقاطعة المساعد فور بدء المتصل بالكلام.
- اختبار الصمت والضوضاء وضعف الشبكة.
- اختبار إنهاء المكالمة وإغلاق جلسة API.
- اختبار fallback إلى مسار SIP المعتاد عند تعطل Gateway أو رفض API.

**بوابة النجاح:** 20 مكالمة اختبار متتالية دون فقدان مسار الجسر أو تداخل صوت بين الجلسات، مع توثيق زمن الاستجابة.

### المرحلة 4 — التوسع
- اختبار مكالمتين ثم 5 ثم 10 ثم 20 مكالمة متزامنة.
- قياس حدود API الفعلية والاتصالات والذاكرة والحرارة على أجهزة Android.
- ضبط حدود الجلسات والتكلفة والتنبيهات.
- لا يُعلن دعم 20 قناة قبل اختبار ضغط فعلي موثق.

## 8. معايير الاختبار والتشخيص

لكل مكالمة نسجل metadata فقط:
- call/session ID مستعار.
- provider/model والـ codec ومعدل العينة.
- وقت إنشاء الجلسة وزمن أول صوت وارد وأول رد صوتي.
- عدد إطارات الصوت المرسلة/المستلمة والإطارات المفقودة.
- VAD events، interruptions، reconnects، usage، وسبب الإنهاء.
- لا نسجل أرقام الهاتف كاملة أو مفاتيح API أو صوت PCM أو نص المحادثة افتراضياً.

حالات الاختبار:
1. صوت ثنائي الاتجاه.
2. المتصل يتكلم أثناء رد المساعد (barge-in).
3. المتصل يتوقف لفترة قصيرة ثم يكمل.
4. ضوضاء وخسارة حزم/تذبذب اتصال.
5. رفض المصادقة أو نفاد الرصيد أو تجاوز rate limit.
6. إغلاق WebSocket أثناء المكالمة.
7. إنهاء SIM call قبل إغلاق AI session.
8. تعطيل AI والرجوع إلى الجسر الحالي.
9. جلستان متزامنتان للتأكد من عزل الصوت.
10. فحص عدم ظهور API key في APK أو logcat أو تقارير التشخيص.

## 9. الأمان وحدود الموافقة

- مفتاح OpenAI محفوظ على الخادم فقط.
- تشفير النقل، ومصادقة كل جهاز، وتدوير الأسرار.
- عدم تشغيل AI تلقائياً على كل مكالمة قبل تفعيل المستخدم.
- إعلان واضح للمتصل أن الرد آلي.
- لا تسجيل للصوت أو تخزين transcript إلا بخيار صريح وسياسة احتفاظ واضحة.
- لا إجراء لمكالمات صادرة أو رسائل أو تحويلات مدفوعة دون سياسة موافقة منفصلة.

## 10. ما لا نفعله في هذه الخطة

- لا نضيف Asterisk.
- لا نستبدل SIP registrar أو SIP/RTP bridge الحالي.
- لا نغيّر آلية Shizuku أو TELEPHONY_TX/RX.
- لا نضع API key داخل تطبيق Android.
- لا نفتح منفذاً عاماً جديداً قبل تحديد المصادقة وTLS.
- لا نفعّل AI افتراضياً ولا نرسل مكالمات حقيقية للاختبار دون إذن.
- لا ندمج الفرع ولا ننشر APK/خدمة إنتاجية تلقائياً.
