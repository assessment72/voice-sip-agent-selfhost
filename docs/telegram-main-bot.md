# بوت Telegram الرئيسي — voice-sip-agent-selfhost

## التصميم المعتمد

- بوت واحد فقط بوصفه واجهة التحكم المركزية.
- يستقبل Hosted API تحديثات Telegram عبر Webhook على `POST /v1/telegram/webhook`.
- يعمل webhook ضمن FastAPI الموجود على Vercel؛ لا يحتاج إلى VPS أو خادم دائم منفصل لتشغيل مستهلك Telegram.
- MongoDB Atlas هو مخزن حالة طلبات التأكيد ومنع تكرار تحديثات Telegram.
- لا يُستخدم `getUpdates` بالتوازي مع Webhook على رمز البوت نفسه.

## تنبيه التوافق مع PR #13

PR #13 يحتوي على عميل Android يستخدم Telegram `getUpdates` long polling. Telegram لا يسمح بتشغيل long polling وWebhook في الوقت نفسه على رمز البوت ذاته. لذلك:
- لم نعدّل PR #13 أو نغلقه أو ندمجه.
- لا تضع رمز البوت نفسه في عميل Android وفي Vercel في آن واحد.
- عند اعتماد Webhook المركزي، يجب إيقاف polling للرمز نفسه قبل ضبط Webhook. هذا التغيير التشغيلي لم يُنفذ هنا.

## الأمان

اضبط القيم التالية في Vercel Preview أولاً، بوصفها Encrypted Secrets/Environment Variables:

- `TELEGRAM_BOT_TOKEN`: رمز البوت من BotFather.
- `TELEGRAM_WEBHOOK_SECRET`: قيمة عشوائية قوية مستقلة، يرسلها Telegram في ترويسة `X-Telegram-Bot-Api-Secret-Token`.
- `TELEGRAM_ALLOWED_USER_IDS`: أرقام Telegram الرقمية المصرح بها، مفصولة بفواصل. إذا كانت فارغة فلن يُسمح لأي مستخدم.
- `TELEGRAM_ACTION_EXECUTION_ENABLED=false`: يبقى التنفيذ الخارجي معطلاً في هذه المرحلة.

لا تضع الرمز أو السر أو قائمة المالكين في Git أو APK أو رسائل Telegram. لا تسجل محتوى الرسائل أو ترويسات التفويض في السجلات.

بعد تجهيز عنوان Vercel، اضبط Telegram webhook يدوياً باستخدام Bot API ومرر السر في `secret_token`. لم يتم ضبط Webhook فعلياً ولم يتم الاتصال بـTelegram في هذه التغييرات.

## الأوامر الحالية

- `/start` و`/menu`: قائمة التحكم.
- `/help`: تعليمات الأوامر.
- `/status` و`/sip` و`/calls`: ردود توضيحية فقط؛ ربط الحالة الحية بالأجهزة ما زال مطلوباً.
- `/whatsapp +9677XXXXXXX | نص الرسالة`
- `/sms +9677XXXXXXX | نص الرسالة`
- `/call +9677XXXXXXX`
- `/publish نص المحتوى`

طلبات WhatsApp وSMS والمكالمة والنشر تُنشئ طلباً معلقاً وتعرض زري تأكيد وإلغاء. التأكيد يسجل الحالة `approved_not_executed` فقط؛ لا يتصل بمزود، ولا ينشئ مكالمة، ولا ينشر شيئاً. لا يُخزن نص الرسالة أو المحتوى الخام في سجل الطلب؛ يُخزن بصمة SHA-256 والوجهة المقنّعة فقط. لذلك لا يمكن تنفيذ الطلب لاحقاً من السجل بعد الموافقة؛ يجب إعادة تقديم محتواه عند بناء مسار التنفيذ.

## حدود التنفيذ الحالي

هذا الأساس يضيف قناة Telegram مركزية وسير موافقات آمن، لكنه لا يدّعي اكتمال CRM أو التسويق أو تنفيذ النشر أو المكالمات من البوت. ربط الأوامر بالعمليات الفعلية يتطلب دمجاً منفصلاً مع صلاحيات المؤسسة والموافقة المسجلة وموافقة المستلم وقيود الإرسال ومفاتيح idempotency وسجل تدقيق. يجب أن يبقى التنفيذ مغلقاً افتراضياً، وأن يطلب البوت تأكيداً جديداً لكل عملية حساسة. كما يجب أن تمر المكالمة بعد موافقة Telegram بموافقة محلية مستقلة على جهاز Android المستهدف قبل التنفيذ.

## الاستضافة وWhatsApp Evolution

Webhook Telegram يعمل على Vercel serverless. هذا لا يعني أن خادم Evolution API الدائم أصبح قابلاً للاستضافة على Vercel؛ جلسات Baileys المستمرة ما زالت تحتاج Runtime دائم وتخزين جلسات دائم. إذا كان شرط المشروع عدم استخدام خادم خارجي، فلا تفعّل Evolution/Baileys على هذا الأساس. يمكن إبقاء موصل Evolution معطلاً، ثم تنفيذ تكامل WhatsApp Cloud API الرسمي مباشرة من Vercel في مرحلة مستقلة. لا توجد رسائل حقيقية أو عمليات نشر أو مكالمات في هذا التنفيذ.
